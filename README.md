# Tunnel AC

> **English summary** — Android app pair that detects road tunnels by GPS and switches the vehicle's
> climate to recirculation on entry and back to fresh air/auto on exit. `:app` runs on the phone,
> `:relay` runs on a rear-seat Android display and forwards commands over BLE to the car's CAN interface.
> Personal, non-commercial hobby project. **Use at your own risk** (see below).

**지원 환경**: 릴레이는 WWC2 헤드유닛(`com.wwc2.canbussdk`) + Tesla CAN 박스(RZ-TS05)에서 확인했습니다. 그 외 기기·차량은 동작을 보장하지 않습니다.
**지원하지 않는 기능**: 조수석 시트 이동(시험했으나 이 장비에서 동작하지 않아 제거).

## 설치
- 릴리스 APK는 저장소의 **Releases** 에서 받습니다(저장소에는 APK를 올리지 않습니다).
- 폰에는 `app`, 리어 디스플레이에는 `relay` 를 설치하고, 릴레이 앱에 표시/설정한 6자리 PIN을 폰 앱 설정에 같은 값으로 입력합니다.

터널 진입/진출을 GPS로 감지해서 공조를 자동 전환하는 안드로이드 앱.
- **터널 진입** → 항상 **내기순환(RECIRC)**
- **터널 진출** → 설정의 "터널 진출 시 외기로 전환"이 켜져 있으면 **외기(FRESH)**,
  꺼져 있으면(기본) 외기로 강제하지 않고 터널에서 걸어 둔 내기 강제만 풀어 **차량 오토에 제어권을 돌려준다**
  (내부적으로 오토 복귀 명령 1회. 차량 공조는 평소 오토로 두고 쓰는 것을 전제로 한다)

이 저장소는 두 개의 앱(모듈)으로 구성된다.
- `:app` — **폰 앱**. GPS로 터널을 감지하고 공조 전환을 판단한다(갤럭시 등 폰에 설치).
- `:relay` — **릴레이 앱**. 차량 안드로이드 헤드유닛(GPS 없음)에 설치. 폰 앱이 블루투스로 보낸
  공조 명령을 BLE로 받아 헤드유닛의 CAN 서비스(`com.wwc2.canbussdk`, WWC2/RZC Tesla 프로토콜)로 전달한다.
  (자세한 내용은 아래 "헤드유닛(WWC2) 릴레이 동작 방식" 참고)

공조 제어 경로는 두 가지다.
- **시뮬레이션**(기본): 메모리 상태만 바꾸고 로그를 남긴다(하드웨어 없이 로직 검증용).
- **BLE 릴레이**: 설정에서 "릴레이로 실제 차량 공조 제어"를 켜고 릴레이 앱의 PIN을 입력하면,
  실제 차량 공조가 전환된다(아래 "폰 ↔ 리어 디스플레이 연결" 참고).

## 빌드 방법 (Android Studio)

1. Android Studio (최신 버전)로 이 폴더를 연다. Gradle 8.7 wrapper가 포함되어 있으므로(AGP 8.5.2 필수 버전) Android Studio가 자동으로 이 버전을 내려받아 사용한다.
2. `local.properties.example` 을 복사해 `local.properties` 로 만들고 `sdk.dir` 을 채운다(Android Studio가 자동으로 채워주기도 함). 지도는 OpenStreetMap(osmdroid)이라 API 키가 필요 없다.
3. Gradle Sync 실행.
4. `app` 모듈을 실제 기기에서 실행 (에뮬레이터는 GPS 정확도 시뮬레이션이 불안정하므로 실기기 권장).

## 지도 (OpenStreetMap / osmdroid)

지도 탭은 OpenStreetMap 타일을 osmdroid 로 표시한다(키·가입 불필요, 원래 색상 그대로 표시).
- OSM 타일 정책에 따라 앱 고유 User-Agent 를 설정하고, 지도 하단에 OSM 출처를 표시한다.
- 타일 캐시는 앱 캐시 폴더(`cache/osmdroid`)에 저장되며 저장소 권한이 필요 없다.
- 개인용 확인 화면 수준의 사용을 전제로 한다(대량 다운로드/오프라인 저장은 정책상 금지).

## 실행 시 필요한 권한

앱 최초 실행 시 아래 권한을 순서대로 요청한다.
- 위치 권한 (정확한 위치, `ACCESS_FINE_LOCATION`)
- 알림 권한 (Android 13+, `POST_NOTIFICATIONS`)
- 백그라운드 위치 권한 (`ACCESS_BACKGROUND_LOCATION`) — 포그라운드 위치 허용 후 별도 요청됨. 설정에서 "항상 허용"을 선택해야 백그라운드에서도 터널 감지가 계속된다.

추가로 기기 설정에서 다음도 확인하는 것을 권장한다.
- **배터리 최적화 제외**: 설정 > 배터리 > Tunnel AC > 제한 없음 (제조사마다 메뉴 위치가 다름). 제외하지 않으면 백그라운드에서 GPS 업데이트가 지연되거나 서비스가 종료될 수 있다.

## 사용 순서

1. **설정** 탭에서 "터널 데이터 갱신"을 눌러 Overpass API에서 전국 터널 데이터를 받는다 (최초 1회, 이후 필요시).
2. **지도** 탭에서 받아온 터널 위치(폴리라인)를 눈으로 확인한다.
3. **상태** 탭 또는 알림/삼성 루틴을 통해 감지 서비스를 시작한다.
4. 주행 중 터널 진입 300m 전부터 자동으로 내기순환으로 전환되고, 진출 300m 이후 원래 상태로 복귀한다 (현재는 시뮬레이션 로그만 남고 실제 차량 공조는 바뀌지 않음).
5. **로그** 탭에서 진입/진출 이벤트(위치, 속도, GPS 정확도, 공조 상태 변화)를 확인하거나 CSV로 내보내 검증한다.

## 삼성 모드 및 루틴 연동

앱이 정적 바로가기(`start_detection`, `stop_detection`)를 등록해두었으므로,
삼성 [모드 및 루틴] 앱에서 "동작 추가 > 앱 > Tunnel AC" 를 선택하면 "터널 감지 시작/정지" 세부 동작이 나타난다.
이를 이용해 예를 들어 "블루투스가 차량과 연결되면 → 터널 감지 시작" 같은 루틴을 만들 수 있다.

## 폰 ↔ 리어 디스플레이 연결 (BLE / GATT)

연결 방식은 **BLE(GATT)** 이다. 이 디스플레이에서 검증된 구조(릴레이 = GATT 서버, 폰 = 클라이언트,
PIN + HMAC 인증)를 그대로 따른다. **블루투스 페어링은 필요 없다.**

- 리어 디스플레이(`:relay`) = BLE 주변기기. 서비스 UUID(`7ec1b2a0-...`)를 광고하고 명령을 대기.
- 폰(`:app`) = 서비스 UUID 로 스캔해 연결하고 PIN 인증 후 연결한다(연결 시점·유지 방식은 아래 "연결 방식" 참고).
- 명령은 모드 코드 1바이트(1=내기순환, 2=외기, 3=오토)를 CMD 특성에 쓰는 것이며, 쓰기 응답 성공 = CAN 전송 성공이다.
- 프로토콜 상수는 양쪽 `RelayProtocol.kt` 가 동일해야 한다.
- 릴레이는 부팅·ACC 깨어남·블루투스 ON/OFF 때 서버를 다시 열고, 30초마다 자가 점검한다.

**최초 1회 준비**
1. 리어 디스플레이에 `:relay` 앱을 설치하고 한 번 실행한다(이후 부팅 시 자동 실행). 화면에 **PIN(6자리)** 이 표시된다.
   "릴레이 서비스 시작"을 누르면 `BLE: 광고 중` 으로 바뀐다. "로컬 테스트" 버튼으로 CAN 전송을 바로 확인할 수 있다.
2. 폰 앱 **설정 > 리어 디스플레이 릴레이**에서 "릴레이로 실제 차량 공조 제어"를 켜고(근처 기기 권한 허용),
   릴레이 앱에 표시된 **PIN 을 입력**한다.
3. **릴레이 테스트**를 누른다. "릴레이 전송 성공"이 뜨고 릴레이 앱에 "폰 연결: 연결됨 ✓"이 표시되면 정상이다.
   실패하면 토스트에 원인이 표시된다(PIN 불일치, 릴레이 미발견, 권한 필요 등).

릴레이를 끄면(또는 PIN 미입력) 시뮬레이션으로 동작한다.

**내기 유지 모드 (릴레이)**
- 폰이 내기순환 명령을 보내면 릴레이가 "내기 유지 모드"로 들어가, 차량 CAN 의 내기순환 상태(`IN_OUT_LOOP`)를
  계속 감시한다(수신 전용). 유지 중에 내기가 풀리면(1.5초 이상) 내기순환을 다시 보낸다
  (최소 3초 간격, 연속 5회 한도 후 60초 대기).
- 외기 또는 오토 명령을 받으면 유지 모드가 종료된다. 안전장치: 최대 30분, 폰 연결이 2분 이상 끊기면 해제.
- 릴레이 화면에 유지 모드 ON/OFF, 차량 내기순환 상태, 재전송 횟수가 표시되고 로그에 기록된다.
- 주의: 오토 상태에서 강제한 내기가 계속 ON(`IN_OUT_LOOP`=true)으로 읽히는지는
  실차 확인이 필요하다. 계속 OFF 로 읽히면 재전송 한도까지 반복될 수 있으니 로그를 확인할 것.

**주의**
- 같은 디스플레이에서 BLE 광고를 쓰는 다른 앱과 동시에 실행하면 BLE 광고 슬롯이 부족할 수 있다
  (릴레이 BLE 상태에 `광고 실패 code=2` 표시). 그 경우 둘 중 하나를 끄거나 앱을 합쳐야 한다.
- 폰은 Android 12+ 에서 "근처 기기" 권한(스캔·연결)이 필요하다. Android 11 이하는 위치 권한으로 스캔한다.

## 헤드유닛(WWC2) 릴레이 동작 방식

릴레이는 이 헤드유닛 순정 런처(`com.wwc2.mainapp`)가 하단 공조 바에서 쓰는 것과 **같은 경로**로 공조 키를 보낸다.
(`:relay/WwcCan.kt`, `CanSender.kt`, `CarAirMonitor.kt`. 순정 APK 분석으로 확인한 값이며 AIDL 파일 없이 Binder transact 로 직접 구현했다.)

- **연결**: `com.wwc2.canbussdk` 의 `MainService` 에 바인드(액션 `com.wwc2.canbussdk.MainService`). `ICanbusDriver` 를 transact 로 호출.
- **전송**: `sendCanbusCmdToSDK(module=CarSettingsCanBusLogic, 4, Bundle)` [트랜잭션 13].
  Bundle = `Array`="CAR_STATE_ENABLE", `cmd`=프레임 타입(byte), `cmd_int`=0, `CAR_STATE_ENABLE`=데이터(byte[]).
  공조는 프레임 타입 **0x84**, 데이터 `[키코드, 1]`(누름) 후 200ms 뒤 `[키코드, 0]`(뗌).
- **키 코드**: 순환 전환 **0x13(19)** (오토→내기→외기 순으로 돌아가며 바뀜 — 사용자 관찰값이며 로그의 `순환 전환 완료 … (키 N회)`로 확인 가능), AUTO(공조 전체) 0x22(34)는 순환에 영향 없음(실측).
- **상태 읽기**: `registerCallback`(콜백)과 `getAirconditionData()` 의 Bundle 에서 `IN_OUT_LOOP`, `AQS_INNERLOOP` 를 읽는다.
  **실측 판정**: 내기 = loop 1 · aqs 0, 오토 = loop 1 · aqs 1, 외기 = loop 0.
- **전환 방식**: 설정 명령이 없고 순환 키뿐이다. 현재 모드를 읽어 목표와 다르면 키를 누르고, 0.7초마다 다시 읽어
  목표가 될 때까지 **최대 3회** 누른다(순환 순서를 몰라도 동작). 이미 목표면 전송하지 않고, **현재 모드를 읽지 못하면
  전송하지 않고 실패**로 돌려준다. 폰 앱 모드 코드 1=내기 / 2=외기 / 3=오토(순환 오토)는 그대로.
- **내기 유지(터널) 모드**: 강제 내기(loop 1 · aqs 0)일 때만 충족으로 본다. 외기나 오토로 읽히면(오토는 내기/외기를 구분할 수 없음)
  1.5초 뒤부터 내기 명령을 다시 보낸다(최소 3초 간격, 연속 5회 후 60초 휴식). 각 전송은 위 "전환 방식"대로 확인·반복한다.
- 진단 로그: 값이 바뀔 때마다 `공조 값[조회/콜백]` 에 번들의 **모든 키=값**이 남는다(오토 내기/외기 비교용).

**실차 확인이 필요한 항목** (분석만으로 확정하지 못함)
1. `IN_OUT_LOOP` true 가 실제로 **내기**인지(릴레이 화면의 "차량 내기순환" 표시와 차량 화면을 비교).
2. `getAirconditionData()` Bundle 에 `IN_OUT_LOOP` 키가 있는지 — 릴레이 로그에 `공조 Bundle 키(...)` 가 한 번 출력된다.
   키가 없고 콜백도 오지 않으면 상태를 모르는 것으로 보고 전환하지 않는다(로그에 사유 표시).
3. AUTO 키(0x22)가 이미 오토일 때 다시 눌러도 안전한지(토글로 동작하면 수동으로 바뀔 수 있음).
4. 시험은 **정차(P단)** 에서, 릴레이 앱의 "로컬 테스트" 버튼으로 먼저 한다.

그 밖에: 헤드유닛 부팅/ACC 브로드캐스트 이름(`action_acc_wakeup` 등)과 BLE 광고 지원 여부는 이 기기에서 아직 확인하지 않았다.

## 알려진 제한 사항 / 다음 단계

- **공조 제어 경로**: 기본은 `SimulatedHvacController`(가상). 설정에서 릴레이를 켜면 `BleRelayHvacController`(BLE)로 실제 차량이 제어된다. 둘 다 `HvacController` 인터페이스 구현이라 엔진/서비스 로직은 공통이다. 릴레이 앱의 CAN 호출은 모두 try/catch로 감싸 실패해도 죽지 않는다.
- **릴레이 앱 권한**: 릴레이는 Android 12+ 헤드유닛에서 "근처 기기"(`BLUETOOTH_ADVERTISE`·`BLUETOOTH_CONNECT`) 런타임 권한이 필요하다(서비스 시작 시 요청). 폰(Android 12+)도 릴레이 스위치를 켤 때 같은 권한을 요청한다.
- **Overpass 데이터는 수동 갱신**(터널과 입구 접근도로를 함께 받는다): 도로 준공/개통 정보가 최신이 아닐 수 있으므로 주기적으로 "터널 데이터 갱신"을 눌러줄 것.
- 빌드 중 오류를 발견하면 Issues 로 알려주세요.

## 연결 방식 / 시작·정지 동작 (최신)
- **연결 시점**: 폰은 터널 입구 500m 이내로 접근하면 릴레이에 연결한다(이후 명령 전송·상태 확인 때도 필요 시 연결). 마지막 명령 30초 후 연결을 끊는다. 연결 후 12초 안에 인증이 끝나지 않으면 끊고 다시 연결한다.
- **릴레이 인증 제한**: 연결만 하고 10초 안에 인증하지 않은 폰은 릴레이가 끊고 로그에 남긴다.
- **전송 대기**: 명령 1회 최대 약 5초(연결 3초 + 재시도 2초). 실패하면 4초 간격으로 재시도하고, 이벤트 로그에 실패 사유가 남는다.
- **서비스 시작 직후**: 즉시 릴레이에 연결해 차량 공조(내기 여부)를 한 번 확인한다. 실패하면 1분 간격으로 최대 10회 재시도. 결과는 상태 탭과 이벤트 로그에 표시된다. (차량이 알려 주는 값은 '내기/내기 아님'뿐이라 외기와 오토는 구분되지 않는다.) 이 기능은 릴레이 앱도 최신 버전이어야 한다.
- **서비스 정지**: 정지 버튼·알림 정지·바로가기 모두 감지를 멈춘 뒤 릴레이에 오토 복귀 명령을 보내고 종료한다(연결 안 되면 최대 약 8초 시도 후 종료).
- **지도 탭**: 폰 GPS 현위치를 중심으로 표시하며, 손으로 움직이면 따라가기가 멈추고 '내 위치' 버튼으로 복귀한다.
- **DB**: 이벤트 테이블에 부가 설명 열 추가(v2, 기존 기록 유지).
- **진입 시 차량 공조 기록**: 내기순환 명령 직전과 2초 뒤에 릴레이에서 차량 공조(내기/외기)를 읽어 이벤트 로그에 `차량 공조: 외기 → 내기`로 남긴다(내기가 아니면 외기로 표기, 오토는 구분하지 않음). 읽지 못하면 `확인 불가`, 전환 후에도 내기가 아니면 `(내기 전환 확인 안 됨)`을 덧붙인다.
- **진출 판정 수정**: 차량이 터널 끝점을 넘어서면 진행거리를 `터널 길이 + 끝점까지의 직선거리`로 계산한다. (이전에는 진행거리가 터널 길이에서 멈춰 '진출 트리거 거리'에 도달하지 못했고, 경로 이탈 안전 처리로만 진출됐다.)
- **터널 데이터 받기(이어받기)**: 전국을 격자 구역으로 나눠 받으며, 구역 하나를 받을 때마다 바로 저장하고 완료 목록을 기록한다. 끊기거나 중지/종료돼도 버튼이 `이어받기 (n/m 완료)`로 바뀌어 남은 구역만 이어서 받는다. 3구역 연속 실패하면 자동 중단한다. 설정 화면을 벗어나도 앱 안에서 계속 진행된다.
- **병합 직후 안전 처리 오판 수정**: 연속 터널 병합 직후에는 이탈 감시를 켜지 않고, 차량이 다음 터널 도로에 실제로 들어선 뒤부터 적용한다. 접근 중 다음 입구에서 시작 거리보다 100m 넘게 멀어지면 안전 진출한다. 안전 처리 기준은 `max(도로 허용치+150m, 진출 트리거+100m)`로 항상 정상 진출보다 뒤에 온다.

## 알림음
- 설정 탭 '알림음' 카드: 사용 스위치(기본 ON), 소리 크기(0~100, 기본 70), 진입/진출음 미리듣기.
- 진입 = 콜사인(res/raw/entry_callsign.mp3), 내기 해제(정상·안전·강제 진출) = 상승 3음 차임 띠리링(res/raw/exit_chime.m4a). 병합·서비스 정지는 소리 없음.
- 음원은 길이를 줄여 사용: 진입음 약 0.86초(띵똥, 콜사인), 진출음 약 0.70초(띠리링).
- 오디오 용도는 내비게이션 안내음(USAGE_ASSISTANCE_NAVIGATION_GUIDANCE). 설정 변경은 즉시 저장.

## 교차 도로 오인식 방지 / 표기 정리
- 진입 판정에 '터널 진행 방향 검사' 추가: 차 진행 방향이 입구에서 터널 안쪽(폴리라인 약 40m 지점) 방위와 headingTolerance 이내여야 진입(직각 교차 도로 제외). BLE 준비(prepare)에도 동일 적용.
- 로그의 공조 표기는 내기/외기(AUTO는 외기), 상태 탭 차량 공조는 내기/외기로 표기. CSV는 원본 값 유지.
- 지도 내 위치 표시를 빨간색으로 변경(이동 중 빨간 방향 화살표, 정지 시 빨간 점).
- 앱 아이콘 배지(1) 제거: 알림 채널 tunnelac_running_v2(setShowBadge=false)로 교체, 알림 BADGE_ICON_NONE.
- 터널 옆 도로 오인식 방지: (1) 진입 시 터널 입구축에서 옆으로 40m 초과 벗어난 경우 진입 제외(ENTRY_LATERAL_MAX_M), (2) 진입 후 입구를 50m 지나도 터널 도로 30m 이내로 확인되지 않으면 안전 처리로 즉시 취소(ENTRY_CONFIRM_PROGRESS_M).
- 기본값 변경: 진출 트리거 100m, 방향 허용각 60°(기존 저장값은 1회 자동 갱신). 터널 옆 도로 대책 완화: 진입 옆간격 검사 삭제, 입구 50m 통과 후 터널선에서 90m 초과 시에만 취소.
- 로그 하단 표기 통일('공조: A → B'). 진출 로그는 명령한 모드(외기 또는 오토(내기/외기))를 기록하고 전송 실패는 비고에 표시.

## 진입 판정 요약 (최신)
진입은 아래 조건을 **모두** 만족할 때 판정한다(설정값은 기본값).

| 단계 | 조건 |
|---|---|
| 기본 | GPS fix 있음, 속도 ≥ 10km/h, 터널 길이 ≥ 200m |
| 거리·방향 | 입구까지 ≤ 200m, 진행 방향이 입구 방향 ±60°, 터널 안쪽 방위(입구에서 약 40m 지점) ±60° |
| 출구 전용 끝 제외 | 접근도로가 반대쪽 끝에만 있으면 이 끝으로는 진입하지 않음 |
| 접근도로 일치 | 최근 경로(≤600m, 정확도 ≤30m)가 접근도로·터널선 ±15m 안에서 연속 60m 이상, 진행 방향 ±35° (이력 60m 미만이면 통과) |
| 인접도로 비교 | 최근 100m에서 접근도로보다 인접도로가 `max(5m, 정확도×0.5)` 이상 더 가까운 점이 절반 초과면 진입 불가 |
| 예외(기존 방식) | 입구 접근도로가 없거나 가장 긴 선이 100m 미만이면 접근도로·인접도로 검사 생략 |

진입 후: 터널선 30m 이내·방향 ±30° 확인, 이탈 시 안전 진출(터널 중간 80m 초과 이탈, 인접도로 우세 3회·30m 이동 등), 정상 진출은 터널 끝 +100m(GPS 정확도 ≤60m일 때만 판정).
로그: 진입 이벤트에 "근거: 접근도로 Xm, 인접도로 Ym" 기록.

모의 주행 결과(200m 이상 터널 3,587개, 위치 오차 σ=3.5m): 옆도로 오진입 26.6% → 2.6%, 정상 진입 99.5%. 실주행 확인: 송도 동춘지하차도 구간 오진입 수정 후 정상 동작.

## 접근도로(지도) 기반 진입 판정
터널 위를 지나는 고가·교차 도로나 옆길에서 좌회전해 지나가는 경우를 터널 진입으로 오인하지 않도록, 지도의 도로망과 최근 이동 경로를 맞춰 본다.

- **데이터**: '터널 데이터 갱신' 때 터널 입구마다 주변(반경 약 550m)의 도로(고속~3차 도로·램프·소로, 보행/자전거/service 제외)를 함께 받아 저장한다(DB v3, `approach_roads`). 입구 끝 노드에서 도로 노드 연결을 거꾸로 따라가 **입구로 실제 주행해 들어올 수 있는 도로만 약 500m** 남긴다(일방통행 방향 반영). 합류하는 옆길은 합류점에서 100m까지만 포함한다. 터널과 이어지지 않는 평행·교차 도로는 저장하지 않는다.
- **판정**: 입구 200m 이내에서 최근 이동 경로(최대 600m, 정확도 30m 이하 fix)가 접근도로 또는 터널선 ±15m 안에서 **연속 60m 이상** 이어지고, 현재 진행 방향이 그 도로 방향과 ±35° 이내일 때만 진입으로 본다. 접근도로 데이터가 없거나 이력이 60m보다 짧으면 기존 방식(거리·방향)으로 판정한다.
- **터널 안 확정**: 터널선 30m 이내를 지나가도, 진행 방향이 그 지점 터널 방향과 ±30° 이내일 때만 '터널 도로에 들어섬'으로 인정한다(위를 가로지르는 도로 제외).
- **빠른 취소**: GPS가 정상일 때 터널 중간부에서 터널선으로부터 80m 넘게 벗어나면 즉시 안전 진출 처리한다(기존 180~200m).
- **적용 방법**: 업데이트 후 설정에서 '터널 데이터 갱신'으로 받거나(서버가 불안정하면 아래 'PC에서 접근도로 오프라인 계산' 권장) 완성된 `.tac`를 가져온다. 받기 전에는 기존 방식으로 동작한다.
- **한계**: OSM에서 접근도로와 터널 노드가 이어져 있지 않으면 그 입구는 접근도로가 비어 기존 방식으로 판정한다. 터널과 같은 방향으로 15m 이내에 붙은 평행 도로는 구분하기 어렵다. 실주행 검증은 진행 중이며 결과는 아래 '진입 판정 요약'과 CHANGELOG.md 를 따른다.
- **지도 표시**: 지도 탭에서 터널은 파란색, 접근도로는 주황색으로 보인다. 접근도로는 지도를 확대(줌 14 이상)했을 때 보이는 영역만 그린다(최대 1500개 선).
- **갱신 안정화**: 접근도로 요청은 입구 6곳씩 묶어 1초 간격으로 보내고, 실패하면 절반씩 나눠 다시 시도한다. 1곳까지 나눠도 실패하면 그 입구만 건너뛰어(기존 방식으로 판정) 구역 전체가 막히지 않는다. 429/504는 대기 시간을 늘리고, 실패 시 마지막 오류 내용을 상태 문구에 표시한다.
- **받는 순서**: 구역은 북쪽(위도 높은 쪽)부터 받는다.

## 터널 데이터 내보내기 / 가져오기 (.tac)
- 설정 탭 '터널 데이터' 카드의 **데이터 내보내기**로 저장된 터널·접근도로를 `tunnelac-data-YYYYMMDD.tac` 파일(gzip 압축 JSON)로 만들어 공유(메신저·드라이브·메일 등)할 수 있다.
- 받은 사람은 **데이터 가져오기**로 파일을 고르면 터널·접근도로 개수를 확인한 뒤 바로 적용된다(기존 터널·접근도로는 교체, 이벤트 로그·설정은 유지). 적용은 한 트랜잭션이라 실패하면 원래 데이터가 유지된다.
- 파일 형식: 헤더(`format=tunnelac-data`, `version`, `createdMs`, `appVersion`, 개수, `source`) + `tunnels` + `approaches` 배열. 더 높은 버전의 파일은 앱 업데이트를 안내하고 거부한다.
- 터널 데이터를 받는 중에는 가져올 수 없다. 가져온 뒤 감지가 이미 실행 중이면 정지 후 다시 시작해야 새 데이터가 반영된다.
- 데이터 출처는 OpenStreetMap contributors (ODbL)이며, 파일을 공유할 때도 출처 표기를 유지해야 한다.
- **받는 중 상태·시간 한도**: 구역 안 진행(터널 조회 / 접근도로 n/m 묶음 · 건너뜀)을 화면에 표시한다. 한 구역의 접근도로 수집은 15분(쉰 시간 제외)을 넘기거나 쉬는 횟수가 3회를 넘으면 남은 입구를 건너뛰고(기존 방식으로 판정) 구역을 완료 처리한다(아래 '서버 과부하 대응' 참고). 접근도로 요청은 30초 제한으로 짧게 끊고 나눠 다시 시도한다.
- **네트워크 끊김 대기**: 주소 조회 실패·연결 불가는 실패로 세지 않고 연결이 돌아올 때까지(최대 10분) 기다렸다가 같은 구역을 다시 시도한다. 10분 안에 돌아오지 않으면 받기를 멈추고 '이어받기'를 안내한다.

### 병렬 받기·이어받기
- 접근도로는 서버 2곳(overpass-api.de / private.coffee)에서 동시에 받습니다(묶음 단위, 서버마다 1개 일꾼). 한쪽이 죽으면 다른 서버로 넘어갑니다.
- 묶음(입구 6곳 이하)마다 "받기 → 계산 → 저장 → 완료 표시(approach_done)"를 한 트랜잭션으로 처리하므로, 구역 도중 중단돼도 이어받기 때 끝난 묶음은 다시 받지 않습니다.
- 새 갱신 시작·.tac 가져오기 시 완료 표시는 초기화됩니다. DB 버전 4.

### 접근도로 보완
- 전체 받기가 끝나면 접근도로 완료 표시가 없는 터널(100m 이상)을 점검해 그 터널만 way id로 다시 조회·계산합니다.
- 설정의 "접근도로 보완" 버튼으로 수동 실행도 가능합니다. 묶음 중 일부 입구를 건너뛴 경우 그 묶음은 완료로 표시하지 않아 보완 대상이 됩니다.
- .tac 가져오기 시 접근도로가 들어 있는 터널은 완료로 처리합니다.

### 구역 보기·구역별 갱신
- 지도 화면의 "구역 보기"로 42개 구역(1° 격자, 북쪽 행부터 서→동 번호)을 점선과 번호로 표시합니다. 터널이 있거나 받기 완료된 구역은 초록, 나머지는 회색입니다.
- 칸을 탭하면 아래에 구역 번호·터널 수와 "전체 다시 받기"·"건너뛴 것만 받기" 버튼이 나타납니다. 전체 다시 받기는 터널 조회→접근도로→빈 터널 보완을, 건너뛴 것만 받기는 그 구역에서 접근도로가 빈 터널만 다시 받습니다. 둘 다 다른 구역과 이어받기 상태는 건드리지 않습니다.

### 서버 과부하 대응
- 연속 실패가 8번 쌓이면 구역을 중단하지 않고 모든 일꾼이 60초 쉰 뒤 다시 시도합니다(구역당 최대 3회, 넘으면 남은 묶음은 건너뜀 → '접근도로 보완' 대상).
- 구역 시간 한도는 15분이며 쉰 시간은 한도에서 제외됩니다.
- 한 서버가 3번 연속 실패하면 3분간 쓰지 않고 나머지 서버로 받습니다.

### 터널 하나만 갱신
- 지도에서 파란 터널 선을 탭하면 이름·길이·접근도로 입구 수와 "이 터널만 갱신" 버튼이 나옵니다. way id로 그 터널만 다시 조회해 좌표·이름을 덮어쓰고 접근도로를 새로 계산합니다.

### PC에서 접근도로 오프라인 계산 (`tools/tac_approach_builder.py`)
서버(Overpass)가 불안정할 때, 앱에서 내보낸 `.tac`에 접근도로를 PC에서 계산해 넣는다. 앱과 같은 알고리즘(ApproachBuilder 포팅)을 OSM 한국 추출 파일로 돌린다.
1. 앱에서 "데이터 내보내기"로 `.tac`를 PC로 옮긴다.
2. `pip install osmium`
3. `python tac_approach_builder.py --download` (한국 OSM 파일 받기, 수백 MB 규모)
4. `python tac_approach_builder.py --tac 내보낸.tac --pbf south-korea-latest.osm.pbf --out 결과.tac`
5. 결과 `.tac`를 폰으로 옮겨 "데이터 가져오기". (계산을 마친 터널은 `doneIds`로 표시되어 '접근도로 보완' 대상에서 빠진다.)
- 메모리가 부족하면 `--idx sparse_file_array,임시파일경로` 를 붙인다.
- 데이터 출처: OpenStreetMap contributors (ODbL)

### 인접도로 비교 (옆도로 오인 방지)
- PC 계산기가 터널선·접근도로선 곁(40m 이내)을 지나는 일반 도로(접근도로·터널과 같은 도로 제외)를 `adjacent` 항목으로 `.tac`에 넣고, 앱 DB(v5 `adjacent_roads`)에 저장한다. 끄려면 `--no-adjacent`.
- **진입 판정**: 최근 100m 경로(3점 이상)에서 접근도로보다 인접도로가 `max(5m, 정확도×0.5)` 이상 더 가까운 점이 절반을 넘으면 진입하지 않는다(접근도로 일치 검사에 더해 적용).
- **진입 후**: GPS 정확도 25m 이하일 때만, 터널선보다 인접도로가 같은 여유만큼 더 가까운 상태가 연속 3회이고 30m 이상 이동하면 안전 진출한다(이벤트 로그에 두 거리 기록). GPS가 나쁜 구간에서는 비교하지 않는다.
- 인접도로 데이터가 없는 터널은 기존과 동일하게 동작한다.
- 지도에는 확대 14 이상에서 보라색(4dp)으로 표시된다(접근도로 아래층).

### 짧은 접근도로 입구는 기존 방식
- 입구의 가장 긴 접근도로가 100m 미만이면(실제 진입로가 데이터에 빠졌을 가능성) 접근도로 일치·인접도로 비교를 건너뛰고 거리·방향만으로 판정한다(모의 주행에서 진입 누락 64→21개 터널, 옆도로 오진입은 거의 불변).

### 출구 전용 끝 제외 · 진입 근거 로그
- 접근도로가 한쪽 끝에만 있는 터널(일방통행)은 접근도로가 없는 끝을 출구 전용으로 보고 그쪽 진입은 판정하지 않는다(맞은편 방향 터널의 출구 끝으로 잘못 진입하던 문제). 양쪽 모두 접근도로가 없으면 예전 방식 유지.
- 터널 진입 로그에 "근거: 접근도로 Xm, 인접도로 Ym"(진입 시점 위치에서 가장 가까운 선까지 거리)을 함께 기록한다.
